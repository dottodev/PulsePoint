# PulsePoint

A reaction-time trainer for Android, written in C++.

Four modes, thirty achievements, one greyscale palette, and no systems that are
not about getting faster.

```
SEE  →  REACT  →  SCORE  →  IMPROVE  →  REPEAT
```

---

## What is in the box

| Mode | Question | Shape |
|---|---|---|
| **REFLEX** | How fast can you react? | Ten trials, a delay you cannot predict, one target |
| **FLICK** | React. Aim. Hit. | Twenty targets at random positions, shrinking, up to three at once |
| **FOCUS** | See the target. Ignore the rest. | Twelve groups; one bullseye among look-alikes |
| **MAX** | How long can you survive? | Endless; every clean reaction makes the next one harder, one mistake ends it |

Everything else — the lifetime press counter, the statistics screen, the thirty
achievements, the result breakdown, the personal bests — exists to make the four
numbers above legible over time.

## Building

### Prerequisites

* Android SDK with platform 34, build-tools and platform-tools
* Android NDK 27 (26 also works)
* A JDK 17

### Without Gradle

The project is one Activity, one `GLSurfaceView` and one shared object, so the
whole build is four steps and this script does them:

```sh
export ANDROID_SDK_ROOT=~/Android/Sdk
export ANDROID_NDK_HOME=$ANDROID_SDK_ROOT/ndk/27.1.12297006
tools/build_apk.sh
adb install -r build-apk/PulsePoint.apk
```

`--debug` builds a debuggable APK, `--abi arm64-v8a` builds one ABI (much faster
to iterate on). The script signs with a generated keystore, so the output is
installable straight away and is not a release artifact.

Two portability notes, both handled inside the script. If `JAVA_HOME` is set its
`bin` goes first on `PATH`, so a machine with several JDKs still uses the right
`javac`. And if the NDK's own compiler cannot execute on the build host (there
is no NDK toolchain for Linux on ARM64), the script falls back to a host
`clang++` targeting Android with the NDK sysroot, and shims the two glibc-only
symbols the SDK's `aapt2` needs on musl. Same sources, same flags, same APK.

### With Gradle

```sh
./gradlew :app:assembleRelease     # or open the project in Android Studio
```

`gradle/wrapper/gradle-wrapper.jar` is not committed — a binary jar in the tree
helps nobody and it is generated by any Gradle install:

```sh
gradle wrapper --gradle-version 8.7
```

Both paths compile exactly the same source list with the same flags, from
`app/src/main/cpp/CMakeLists.txt` and the `NATIVE_SOURCES` list in
`tools/build_apk.sh` respectively.

## Verifying it

```sh
tools/verify.sh
```

Five things, none of which need a phone:

1. **Gameplay and persistence tests** (`hosttest/tests.cpp`) — 39 tests covering
   the monotonic clock, RNG determinism, input de-duplication, the score
   formula's anti-spam properties, consistency, reaction-time precision, session
   bookkeeping, lifetime statistics, all thirty achievements, save-file
   round-trip and corruption recovery, every mode's rules, target placement
   bounds (including the HUD exclusion zone), number formatting, synth output
   cleanliness under worst-case voice load, and the embedded font atlas.
2. **Link and screen smoke test** (`hosttest/linktest.cpp`) — compiles the
   renderer, widget layer, all nine screens, the audio synth and the state machine
   against stub OpenGL entry points, then drives a full session: boot, a played
   round, an abandoned round, every sub-screen, a settings pass and a MAX run,
   then reloads the profile and checks the counters survived.
3. **JNI bridge type check** — the one file that needs the NDK headers, checked
   against a minimal shim.
4. **JNI cross-check** — every native method the bridge exports is declared in
   Java with the same arity, and nothing is declared on only one side.
5. **Font atlas reproducibility** — regenerating the atlas produces byte-identical
   output to what is committed.

```sh
python3 tools/build_host_tests.py      # build only
./build-host/pulsepoint_tests score    # run a subset
./build-host/pulsepoint_linktest
```

## How it is put together

```
app/src/main/cpp/
  core/      clock, rng, input routing, geometry, tunables
  game/      session, scoring, the four modes, the app and its screens
  meta/      statistics, achievements, settings, the save file
  gfx/       GL declarations, shaders, the batched renderer
  ui/        widgets, screens, particles, the thirty achievement icons
  audio/     the synthesiser
  generated/ the baked SDF font atlas
  platform/  the JNI bridge
app/src/main/java/com/pulsepoint/app/
  MainActivity   window, insets, lifecycle
  GameView       GL surface, touch capture
  AudioStream    AudioTrack plumbing
  PulsePoint     the native entry points
```

### The five decisions everything else follows from

**1. Timing comes from one clock, and it is not the frame clock.**
`core/clock.h` is `clock_gettime(CLOCK_MONOTONIC_RAW)`. A stimulus is stamped
when the frame containing it is decided; a tap is stamped on the UI thread by
`SystemClock.elapsedRealtimeNanos()` the instant `onTouchEvent` is entered. Both
read the same hardware counter, so they subtract directly at nanosecond
resolution. Nothing anywhere derives a duration from a frame count, a vsync
callback, an animation or a UI timer. Reaction times are stored in microseconds
and displayed in milliseconds, so the stored value is finer than anything shown.

The one correction applied is display latency: a stimulus stamped at frame
submission reaches the eye roughly half a frame later, so `AUTO` calibration
subtracts half the smoothed frame interval, clamped to 0–22 ms and overridable in
Settings. It makes the number measure the finger rather than the compositor.

**2. Input is deduplicated, not debounced.**
A re-delivery of the same physical touch is dropped by three independent rules: a
9 ms floor between accepted taps, a same-spot check for a duplicate arriving one
frame later, and rejection of any second finger while the first is down. The
first two are far below the ~40 ms fastest double tap a human can produce, and
the third is why a two-finger gesture can never register as a reaction. The
lifetime press counter increments on accepted taps only.

**3. Score cannot be farmed.**
A hit is worth `speed x accuracy x consistency x streak x difficulty`. Speed uses
a power curve so the gap between a good and a great reaction is large.
Accuracy is `hits / presses` and is evaluated *at the moment of each hit*, so
mashing during a delay cannot retroactively damage points already earned but
does tank every multiplier that follows. REFLEX is a go/no-go task: every
unanswered press is a full false start. The tests assert the property directly:
forty mashed presses plus one lucky 160 ms hit scores less than a fifth of five
clean 200 ms hits.

**4. The whole frame is two draw calls.**
Shapes are signed distance fields evaluated in the fragment shader, so a 1 dp
hairline and a 200 dp panel cost the same, every edge is analytically
antialiased with no textures, and shapes blend freely in submission order. Text is
one SDF atlas sampled with `fwidth` for an exact one-pixel edge at any size. Two
programs, two dynamic buffers, no render targets, no per-object state changes and
no allocation after load. The renderer is written this way partly for speed and
partly so the maths can be tested on a desktop: only the driver has an opinion
left.

**5. Everything is local and atomic.**
No permissions, no network, no account. The entire profile is one fixed-size
struct written temp-file → `fsync` → `rename`, with the previous good copy kept
as `.bak` and used automatically if the primary fails to validate. A kill, a flat
battery or a full disk can lose the most recent round; it cannot leave a
half-written profile.

## The above-human achievements

Five of the thirty are hidden until they fire, and they are the only ones in the
game that cannot be earned by volume:

| | Threshold |
|---|---|
| HUMAN+ | below 150 ms |
| HYPERREFLEX | below 130 ms |
| OVERDRIVE | below 110 ms |
| TRANSCEND | below 90 ms |
| PULSEPOINT | below 70 ms |

They are **gameplay records, not claims about biology.** Each is a single
measured tap-to-stimulus latency produced by this app on your hardware, and some
of the thresholds sit below what is generally considered attainable with practice
— which is why they are framed as records. The unlock overlay says so on screen
every time one fires, and the achievement list hides the requirement, the name and
the description until then.

A reading under 45 ms is treated as a measurement artefact rather than a
performance: it is recorded and displayed, but it never becomes a personal best
and never unlocks a performance achievement. The guard lives in the evaluator as
well as in the statistics collector, so a hand-edited save file cannot fake one.

## Layout and accessibility notes

* UI is authored against a virtual 380 dp short edge and scales to the device, so
  a tablet is a roomier phone rather than a stretched one, and a dense small phone
  stays readable. The scale is clamped to 0.80–1.45.
* Both the top and bottom window insets are reported to the layout, so no button
  can end up behind a gesture bar or a cutout, and the display lays out against the
  cutout from API 28.
* Every tappable target carries 10 dp of slop, because the game is about vision
  and decision time, not dexterity with a 3 mm radius.
* Sound and music can be switched off independently and the game is fully playable
  with both off. The music bed ducks during a round.
* There is a QUIT control in every round. An abandoned run keeps its real presses,
  samples and time; it is a short run, not a fake one.

## Third-party

* **Orbitron** (Black) and **JetBrains Mono** (Bold) — SIL Open Font License 1.1,
  in `third_party/fonts/` with their licence files. Both are rasterised at build
  time by `tools/gen_font_atlas.py` into a single-channel SDF atlas that is
  embedded in the binary, so the app ships no font files and needs no asset
  pipeline.
* **zlib** — the NDK's copy, used only to inflate that atlas at startup.

Nothing else. No UI toolkit, no asset loader, no physics engine, no analytics, no
networking.

## Regenerating the font atlas

The generated sources are committed, so a normal build never needs Python. To
change the faces or the rasterisation parameters:

```sh
python3 tools/preview_font.py /tmp/preview.png   # CPU reference of the shader maths
python3 tools/gen_font_atlas.py
```

`tools/verify.sh` re-runs the generator and fails if the output differs from what
is committed, so the tree can never drift from its own sources.
